## いちばん大事な形

### 1. 写真はユーザーID（UUID）に紐づく

```
ストレージのパス: {ユーザーUUID}/{日時}-{種類}.jpg
テーブル:        stickers.user_id
RLS:            auth.uid() = user_id
```

⚠️ **これが「引っ越しても写真が繋がる」理由であり、UUID を変えてはいけない理由です。**

### 2. `words` は全ユーザー共有、`word_explanations` は組み合わせごと

`words` は `(language, headword)` で1行。**誰の物でもない事実**だけを持ちます
（見出し語・読み・品詞・級・例文・カテゴリ）。

解説は**読む人の言語と母語で中身が変わる**ので、別テーブルに分けてあります:

```
word_explanations (word_id, explain_lang, l1) が一意
```

⚠️ **なぜ分けたか（重要）**: 以前は解説も `words.extras` に載っていて、
表示言語か母語が違う人が開くと**カードを開くたびに解説を丸ごと作り直して上書き**していました。
日本語の人と韓国語の人が同じ「腳踏車」を持っていたら、**互いに開くたび永久に作り直し合う**。

- 遅い（開くたび AI 待ち）
- 高い（同じ語の AI 呼び出しが利用者数×言語数ぶん永久に発生）
- 不正確（同じ語の解説が開くたび揺れる。4択の選択肢まで揺れた前例あり）

いまは**共有キャッシュ**なので、誰か1人が最初に払えば同じ組み合わせの全員がゼロ秒・ゼロ円。

⚠️ `words.extras` と `words.meaning_ja` の**列は残っています**（本番のデータを壊さないため）。
読む側が新しい表を優先します。iPhone 版も同じ順序で読むこと。

### 3. ストレージのバケットは3つ

| バケット | 公開 | 中身 | 実測 |
|---|---|---|---|
| `stickers` | **非公開** | 撮った写真・切り抜き・自撮り・サムネ | 311件 / 132MB |
| `tts` | **非公開** | 作り置きの発音音声 | 4,149件 / 104MB |
| `avatars` | 公開 | プロフィール画像 | 2件 / 39kB |

⚠️ 非公開バケットは**署名付きURL**で配ります。
`tts` は**利用者から書き込めません**（音声を汚されると全員の発音が壊れるため、
書き込みはサービスロールのみ）。

## RLS（行ごとの権限）

ほぼ全テーブルが `auth.uid() = user_id` の形です。
⚠️ **iPhone 版から `supabase-swift` で直接読み書きしても安全なのはこのおかげ。**
RLS を外したり、サービスロール鍵をアプリに埋めたりしないこと。

例外:
- `words` / `dictionary_entries` / `categories` … 全員が読める共有データ
- `app_config` … 管理者のみ

---

## 1日の上限

`usage_events` で数えます（`assertWithinDailyCap`）。
無料/課金の線引きに直結する所です。

| 種類 | 何を数えるか |
|---|---|
| `card` | カードの生成 |
| `tts` | **本当に合成したときだけ**（キャッシュ命中は無料・無制限） |
| `removebg` | remove.bg の呼び出し |
| `journal` | 日記の添削 |

⚠️ iPhone 版で切り抜きが Vision（端末内）になると、`removebg` の計数は不要になります。
**原価が下がる**のはここです。

## Edge Functions

**1つも使っていません。** サーバー処理はすべてアプリ側（TanStack の server fn）にあります。
移行の手間がその分ありません。

## マイグレーションの当て方

⚠️ **リポジトリに Supabase CLI が入っていません。**
55ファイルは Lovable が当てていました。

自分で持つなら:
```
npm i -D supabase
npx supabase link --project-ref <新しいID>
npx supabase db push
```

⚠️ ファイル名が `<日時>_<UUID>.sql` の物は Lovable が生成した物、
`<日時>_<説明>.sql` の物は手で書いた物です。どちらも順に当たります。
